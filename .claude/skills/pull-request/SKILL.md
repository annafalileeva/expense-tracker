# Pull request

Создаёт pull request на GitHub по правилам § "Pull request conventions" из
корневого `CLAUDE.md` этого репозитория.

## Аргументы

`$ARGUMENTS` — два аргумента, **целевая (base) ветка** и **заголовок PR**, в
таком порядке (см. `argument-hint: [base-branch] [pr-title]`):

```
/pull-request <base-branch> "<pr title>"
```

- `<base-branch>` — ветка, в которую вливается PR (обычно `main`).
- `<pr title>` — заголовок PR в формате `<type>(<scope>): <summary>`,
  повелительное наклонение, до ~70 символов (см. § "Commit conventions" —
  формат тот же). Если заголовок состоит из нескольких слов, передавай его
  в кавычках.

**Веткой-источником (head) PR всегда является текущая ветка репозитория** —
скилл не создаёт и не переключает ветки, только читает `git branch
--show-current`.

Если один из аргументов не передан или не разобрать, где base-ветка, а где
заголовок — переспроси у пользователя, а не угадывай.

## Практика

1. **Проверить текущее состояние репозитория:**

   ```bash
   git status
   git branch --show-current
   ```

   Если есть незакоммиченные изменения — не коммитить их самостоятельно
   (это задача скилла `commit`), а сообщить пользователю и предложить
   сначала закоммитить.

2. **Проверить, что текущая ветка не совпадает с `<base-branch>`.** Если
   совпадает — сообщить об этом и не продолжать: PR не может идти из
   ветки в саму себя, а пушить/PR-ить из `main` напрямую запрещено
   правилом GitHub Flow в `CLAUDE.md`.

3. **Проверить, что ветка ушла дальше `<base-branch>` и есть, что
   пуллреквестить:**

   ```bash
   git log <base-branch>..HEAD --oneline
   git diff <base-branch>...HEAD
   ```

   Если коммитов нет — сообщить об этом, не создавать пустой PR.

4. **Запушить текущую ветку на remote:**

   ```bash
   git push -u origin $(git branch --show-current)
   ```

   (Вызов этого скилла пользователем уже считается явной просьбой
   запушить и открыть PR — отдельно спрашивать не нужно.)

5. **Собрать тело PR** по структуре из `CLAUDE.md`, опираясь на
   `git diff <base-branch>...HEAD` (а не на память о том, что планировалось
   сделать):
   - `## Summary` — что реализует PR в терминах пользовательского
     поведения/UI, не файл-за-файлом.
   - `## API changes` — обязательно, если диф затрагивает `apps/api`.
     Новые эндпоинты (метод + путь), для изменённых — до/после формы
     запроса/ответа. Если новых эндпоинтов нет — явно написать "No new
     endpoints".
   - `## Known limitations` (опционально) — осознанные упрощения или
     отложенная работа.
   - `## Test plan` — чеклист того, что реально проверено
     (`npm run typecheck`/`test`/`lint`, ручной `curl` для изменённых
     эндпоинтов, проход в браузере для UI) с `[x]`/`[ ]` по факту, а не
     шаблон.

6. **Создать PR** через heredoc, чтобы многострочный Markdown не ломался
   из-за экранирования в shell:

   ```bash
   gh pr create --title "<pr title>" --base <base-branch> --head "$(git branch --show-current)" --body "$(cat <<'EOF'
   ## Summary
   - ...

   ## API changes
   ...

   ## Test plan
   - [x] ...
   EOF
   )"
   ```

7. **Вернуть пользователю URL созданного PR** (`gh pr create` печатает его
   в stdout).
