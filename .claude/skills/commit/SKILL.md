# Commit conventions

Коммиты оформляются по [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <summary>

<body>
```

## Правила

- **`<type>`** — один из: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`,
  `style`, `perf`, `build`, `ci`.
  - `feat`/`fix` используются только для изменений, влияющих на поведение
    приложения в рантайме.
  - Изменения конфигурации/тулинга/зависимостей — `chore`.
  - Изменения только форматирования — `style`.
- **`<scope>`** — воркспейс или фича, которой касается изменение: например
  `api`, `web`, `database`, `auth`, `expenses`, `categories`. Опускается
  только для изменений, затрагивающих весь репозиторий целиком (например,
  корневой тулинг).
- **`<summary>`** — в повелительном наклонении ("add", а не "added"/"adds"),
  с маленькой буквы, без точки в конце, до ~72 символов.
- **Тело сообщения** (опционально, отделяется пустой строкой) объясняет
  *почему*, а не *что* — что изменилось, и так видно из диффа. Перенос строк
  на ~72 символах.
- **Один коммит — одно логическое изменение**; не смешивай несвязанные
  фичи/фиксы в одном коммите.
- **Breaking changes** — добавляется `!` после типа/скоупа
  (`feat(api)!: ...`) и футер `BREAKING CHANGE:` с описанием миграции.

## Практика создания коммита

1. Проверить `git status` и `git diff` (staged + unstaged), чтобы понять,
   что реально войдёт в коммит.
2. Просмотреть `git log` на предмет стиля последних коммитов этого репо.
3. Стейджить конкретные файлы по имени, не `git add -A`/`git add .` —
   чтобы случайно не утащить секреты или лишнее.
4. Составить сообщение по правилам выше и создать коммит через heredoc,
   чтобы многострочный текст не ломался из-за экранирования в shell:

   ```bash
   git commit -m "$(cat <<'EOF'
   <type>(<scope>): <summary>

   <body>
   EOF
   )"
   ```

5. Коммитить только когда об этом явно просит пользователь — не делать это
   проактивно.
