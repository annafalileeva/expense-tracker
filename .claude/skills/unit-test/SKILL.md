# Unit test

Пишет unit-тесты для файла, переданного аргументом, следуя правилам этого
репозитория (CQRS-структура `apps/api`, § "Architecture" в корневом
`CLAUDE.md` и `apps/api/CLAUDE.md`) и стилю уже существующих спеков, а не
общим best practices "из головы".

## Аргументы

`$ARGUMENTS` — один аргумент, **путь к файлу**, на который нужно написать
тесты (относительный от корня репозитория или абсолютный):

```
/unit-test apps/api/src/modules/expenses/commands/create-expense.handler.ts
```

Если аргумент не передан, путь не существует или указывает не на файл
(например, на директорию) — переспросить у пользователя, а не угадывать.

## Практика

1. **Прочитать целевой файл целиком** (`Read`) — понять, что он экспортирует
   и делает: command/query handler, controller, DTO, React Server
   Action/компонент, чистая утилита и т.п.

2. **Определить workspace по пути** и, соответственно, доступный
   тест-раннер:
   - `apps/api/**` — Jest уже настроен (`npm run test -w @expence-tracker/api`),
     конвенция файла — `<basename>.spec.ts` **рядом** с исходником (не в
     отдельной `__tests__/` папке), см. `commands/*.handler.spec.ts` в
     `modules/auth`.
   - `apps/web/**` — тест-раннер (Jest/Vitest) **ещё не настроен** в этом
     воркспейсе (в `package.json` нет `test`-скрипта). Не устанавливать
     зависимости и не создавать конфиг самостоятельно — сообщить об этом
     пользователю и спросить, настраивать ли раннер с нуля или он сделает
     это отдельно, прежде чем писать сам тест-файл.
   - `packages/database/**` — тесты здесь не приняты (это Prisma-схема и
     сгенерированный клиент, а не логика); уточнить у пользователя, что
     именно он хочет протестировать.
   - Файл, для работы которого нужен реальный Postgres (обращается к
     `PrismaService`/`PrismaClient` напрямую, без DI-моков) — это кандидат
     на e2e (`npm run test:e2e -w @expence-tracker/api`), а не на unit-тест.
     Сказать об этом прямо, а не писать unit-тест, который на самом деле
     ничего не проверяет из-за замоканной насквозь бизнес-логики.

3. **Найти образец для стиля** (`Glob`/`Grep` на `*.spec.ts` рядом или в
   соседних модулях того же типа — handler/controller/util) и следовать
   его конвенциям, а не изобретать новые:
   - Ручные моки зависимостей через `{ execute: jest.fn() }` /
     `jest.fn().mockReturnValue(...)` и прямой `new Handler(...)`, **не**
     `@nestjs/testing`'s `Test.createTestingModule` — см.
     `login.handler.spec.ts`, `register.handler.spec.ts`.
   - `describe`/`it` — заголовки на русском, в духе спецификации ("бросает
     401, если...", "при верном пароле подписывает токен и не отдаёт
     passwordHash").
   - Хелперы-билдеры для тестовых сущностей (`buildUser(...)` и т.п.)
     вместо повторяющихся литералов в каждом `it`.
   - Комментарий с обоснованием только там, где неочевидно (например,
     `// cost=4 — bcrypt быстрее в тестах`), не пересказ действий кода.

4. **Проверить границу модуля** (`apps/api/CLAUDE.md`): мокать нужно то, что
   реально приходит в конструктор тестируемого класса
   (`CommandBus`/`QueryBus`/`TokenService`/`PrismaService` и т.п.), не
   импортировать `PrismaService` или хендлеры из чужого модуля в обход
   `CommandBus`/`QueryBus`.

5. **Написать тест-файл** (`<basename>.spec.ts` рядом с исходником) —
   покрыть:
   - основной happy path;
   - все явные ошибки/исключения, которые бросает код (`UnauthorizedException`,
     `ConflictException`, guard-проверки типа `{ id, userId }` при
     cross-user доступе и т.д.);
   - специфику предметной области, если она есть в файле (например,
     `Decimal`/`formatMoney` для денег, а не `Number()`), а не общий
     шаблонный набор кейсов.
   Не тестировать то, что уже гарантирует фреймворк (`class-validator` DTO,
   Prisma-типы) — это не задача unit-теста хендлера/утилиты.

6. **Прогнать тесты и типы:**

   ```bash
   npm run test -w @expence-tracker/api -- <basename>.spec.ts
   npm run typecheck -w @expence-tracker/api
   ```

   Если тест падает — чинить тест или (если найден реальный баг в
   исходнике) сообщить о нём пользователю отдельно, не переписывать код
   молча за рамками задачи "написать тесты".

7. **Доложить результат**: какой файл создан/дополнен, что покрыто, что
   сознательно не покрыто unit-тестом и почему (например, "требует e2e,
   т.к. обращается к реальной БД").
